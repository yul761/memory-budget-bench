# LongMemEval: StateCore vs mem0 OSS

Both systems were driven by the **same runner**, over the **same question sample**, with the **same answerer and judges**. The memory system is the only thing that differs.

## Result

| system | official judge (gpt-4o) | mem0-style judge (gpt-5) |
|---|---|---|
| **StateCore** | **65.5%** ±6.6 (131/200) | **65.5%** ±6.6 (131/200) |
| **mem0 OSS** | **61.0%** ±6.8 (122/200) | **61.0%** ±6.8 (122/200) |

Difference (official judge): **+4.5 points**, 95% CI ±9.4. **The interval includes zero — this gap is not statistically distinguishable.**

## Reproduction notes

Deviations a reader would otherwise trip over:

- **mem0's published Docker config does not build.** Its harness pins `mem0ai @ git+.../mem0.git@feat/v3-pipeline`; that branch no longer exists upstream. Tested against `feat/oss-add-v3-ingestion-caps` instead.
- **mem0's server code needed a one-line compatibility fix**: current mem0ai rejects a top-level `user_id` in `search()` and requires `filters={...}`. Extraction, storage and ranking are untouched.
- **Internal model is gpt-4o-mini for both, not each project's default.** StateCore normally runs gpt-5-mini, but gpt-5 reasoning models reject the `temperature`/`top_p` that mem0's client always sends, and gpt-4o-mini rejects StateCore's `reasoning_effort`. Parity mattered more than matching either default.
- Scores are **not comparable to either project's published numbers**, which use different answerers, judges and dataset variants.

## Caveat on interpreting these numbers

A LongMemEval score is a property of *system + configuration*, not of the system. The same StateCore build measured on this machine today scored:

| config | score |
|---|---|
| message granularity, top-k 20 | 35% |
| message granularity, top-k 100 | 50% |
| session granularity, top-k 50 | 65.5% |

A 30-point spread from retrieval configuration alone. Quote the config with the number, or the number will not reproduce.
